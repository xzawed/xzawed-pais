# 작업 방법론 — 기획·개발·검증·검토

**프로세스 규칙의 정본이다.** 다른 문서는 여기를 가리키고 자기 규칙을 다시 쓰지 않는다.

## 왜 이 문서가 생겼나 (실측)

문서가 규칙·함정·이력을 축적하는 방식으로만 자라서 **읽히지 않는 크기**가 됐다.

| 측정 | 값 |
|---|---|
| 전체 `.md` 증가 | 611KB → 1.44MB(2.4배) → 개편으로 374KB 로 절단 |
| 절단 후 재증가 | **5일 만에 +15%** |
| 재증가의 집중 지점 | `xzawedManager/CLAUDE.md` **+94%**(17.6KB → 34KB) |
| 그 파일의 함정 섹션 | 전체의 **55%**(18.6KB / 35항목) |
| 프로세스 규칙이 흩어진 곳 | **33개 파일 · 171곳**, 중복 **20그룹**, 모순 **1건** |

그리고 **200줄 게이트는 이것을 못 막는다** — `\n` 개수만 세므로 줄을 길게 쓰면 무한히 자란다.
Manager 는 168줄(84%)인데 루트(200줄)보다 **1.67배 크다**. 줄당 202바이트, 최장 688자.

## 문서는 세 종류뿐이고 수명이 다르다

| 종류 | 무엇 | 수명 | 어디에 |
|---|---|---|---|
| **계약** | 무엇이 참인가 — 타입·스키마·불변식·플래그 태세 | 코드가 사는 동안 | `docs/spec/` · `invariants.md` · `LIVE_VS_FLAGGED.md` |
| **함정** | 코드만 봐서는 모르는 것, 대가를 치른 것 | **가드가 생길 때까지** | 해당 서비스 `CLAUDE.md` |
| **방법** | 어떻게 일하는가 | 방식이 바뀔 때까지 | **이 문서 하나** |

**측정 결과는 문서가 아니다.** "재 봤더니 문제 없었다"는 PR·커밋에 남긴다. 영구 문서에 넣으면
아무도 다시 재지 않는 채로 낡는다.

**`CLAUDE.md` 의 크기 비용은 세션당 발생한다** — 매 세션 컨텍스트에 통째로 로드되기 때문이다.
`docs/services/*.md` 는 필요할 때만 읽는다. 그래서 **지도(무엇이 어디 있는가)는 `docs/services/` 로
보내고 `CLAUDE.md` 에는 계약과 함정만 남긴다.** 크기 상한이 `CLAUDE.md` 에만 걸린 이유가 이것이다.

### 함정의 정상 수명 — 태어나서 죽는다

```
대가를 치름  →  함정으로 기록  →  가드(테스트·스크립트·타입)를 만듦  →  함정을 지우고 가드를 가리킨다
```

**가드가 생겼는데 산문이 남아 있으면 그것이 곧 비대화다.** 함정을 추가할 때 세 가지를 함께 적는다.

1. **왜 코드만 봐서는 모르는가** — 이것이 없으면 함정이 아니라 코드 주석이다
2. **무엇이 대가였나** — 재현 가능한 사실 하나(실패한 CI, 잘못된 통과, 소요 시간)
3. **어떤 가드가 생기면 이 항목을 지우는가** — 죽는 조건

## 파이프라인 — 기획 → 개발 → 테스트 → 실측 → 검토

### 1. 기획 — 표적을 실측으로 고른다

**추측으로 고른 표적은 대개 틀린다.** 무엇을 고칠지 정하기 전에 인벤토리를 기계로 만든다.

- 후보를 **세어** 본다(플래그 목록·호출부·커버리지·크기). 눈으로 훑지 않는다
- 그 결과를 **반증 가능한 이진 명제**로 좁힌다. "안전하다"는 명제가 아니고
  "`X` 조건에서 `Y` 가 등록되지 않는다"는 명제다
- 좁히지 못하면 착수하지 않고 사용자에게 되묻는다

### 2. 개발 — 판정을 검증 가능한 자리에 둔다

- **배선 안에 판정을 직접 쓰지 않는다.** 순수 함수로 떼고 배선은 결과만 소비한다
  — 부를 수 없는 자리에 있는 판정은 아무도 보지 않는다
- **하나를 고치면 같은 종류를 전부 센다.** `grep` 으로 동종 사례를 세고 개수를 커밋에 적는다
- 프로덕션 코드를 테스트 편의로 바꾸지 않는다. 기존 테스트가 이미 쓰는 패턴을 먼저 찾는다

### 3. 테스트 — 봉인은 특정적이어야 한다

- 조건마다 **양방향**으로 고정한다: 충족 시 나타나고, 미충족 시 사라진다
- **반증 절차가 통과 조건이다** — 수정을 되돌려 **의도한 것만** 깨지는지 본다.
  전부 깨지면 봉인이 포괄적인 것이고, 아무것도 안 깨지면 공허한 것이다
- 치환이 실제로 적용됐는지 먼저 확인한다(줄 출력·grep). CRLF·앵커 불일치로 조용히 실패한다
- **반증을 한 방향만 걸면 결론이 못 된다.** "남겨야 한다"만 반증하고 "지워도 된다"를 반증하지
  않으면 낮은 잔존율은 삭제 근거가 아니라 **미검증 상태**다. 지우는 판단에도 반증을 건다
- **메시지가 이름을 대는 것과 실제로 검사하는 것이 같은지** 별도로 봉인한다
- **경고를 중복으로 더하지 않는다.** 이미 더 강한 신호가 뜨는 자리에 좁은 경고를 얹으면 소음이
  되고, 소음이 된 경고는 읽히지 않는다 — 읽히지 않는 경고는 없는 것과 같다

### 4. 실측 — 읽어서 안 것은 아직 모르는 것이다

**이 규칙이 생긴 이유는 실패 5건이다.** 한 세션에서 코드·설정·문서를 읽고 내린 판단이 실행
결과와 반대였던 사례 — 모두 그 잘못된 판단이 저장소 어딘가에 **이미 적혀 있었다**.

| 읽고 믿은 것 | 실행 결과 |
|---|---|
| `buildServer` 는 테스트가 부를 수 없다 | 250ms 만에 기동 |
| advisory 는 검증 없이는 안 돈다 | 기존 테스트가 이미 반대를 단언 |
| 채널 전제 누락이 무음 죽음을 만든다 | 96조합 전수, 무음 **0** |
| org 당 주체는 1명 | 게이트가 이미 org 스코프 |
| 이 CI 스텝은 파일 하나를 돈다 | **58개 파일** |

- **주장은 실행으로 닫는다.** 필요하면 일회용 컨테이너를 띄우고, 조합을 전수로 돌린다
- **CI 로그를 본다.** 잡이 초록인 것과 그 안이 실제로 돈 것은 다르다 — skip 수를 따로 읽는다
- **PR 초록은 master 초록이 아니다.** 머지 후 master 런을 확인한다
- 재현 실패는 숨기지 않는다. 몇 회 시도했고 왜 재현되지 않는지(환경 차이)까지 적는다

### 5. 검토 — 자기 산출물을 남의 것처럼 본다

- 내가 쓴 문서·커밋 메시지·PR 본문도 같은 기준으로 검증한다. 틀리면 조용히 고치지 않고
  **어디가 왜 틀렸는지** 적는다
- **커밋 메시지에 검증하지 않은 주장을 쓰지 않는다.** "이 스텝은 파일 하나를 돈다"를 로그
  확인 없이 적었다가 정정한 사례가 있다
- 같은 실패를 3회 반복하면 멈추고 정리한다 — 시도한 것 / 각각 실패한 이유 / 미확인 가설.
  **CI 로그와 도구의 실제 출력을 코드 추론보다 우선한다**

## Claude · Grok 분담

역할이 겹치면 둘 다 안 쓰게 되므로 경계를 고정한다.

| 협력자 | 역할 | 산출물 |
|---|---|---|
| **Claude** | 아키텍트·통합·머지 결정·정직성 판단 | 설계·PR·최종 판단 |
| **Grok** | 실행·증거·2차 검증 | 후보 diff · 명령 로그 · 반증 판정 |
| **CodeRabbit** | PR 리뷰 의견 | 리뷰 코멘트 |

**위임 가능** — 스펙이 고정됐거나 판단 없이 증거만 필요한 일: 3개 이상 파일의 기계적 편집 ·
격리 워크트리 실증 · 읽기 전용 인벤토리 · **반증**.

**위임 금지** — Grok 이 스스로 자기 실패 지점으로 지목한 영역: 서비스 간 계약(tsc 사각지대) ·
플래그 정직성과 live/dormant 구분 · fail-open ↔ fail-closed 의미론 · 보안 표면 ·
아키텍처와 슬라이스 순서 · 범위가 모호한 "개선" 리팩터 · **설계 의견**.

### 불변 규칙

1. **Grok 출력은 항상 후보다.** 머지 결정은 Claude 가 한다. 요약이 아니라 diff 를 직접 본다
2. **반증으로 넘긴다.** "이게 맞는지 확인해 달라"는 확증 편향을 증폭한다. "이것을 깨뜨려라"로 준다
3. **PASS 주장에 명령 로그가 없으면 안 돌린 것으로 취급한다**
4. **불확실은 FAIL 이다.** 위임 프롬프트에 그렇게 못 박는다

### 위임 크기 — 실측

**하위 검사 총합 6~8개 이내로 쪼갠다.** 블록 수가 아니라 검사 수가 기준이다. 이 한도를 넘기면
600초 타임아웃이 재현된다(8개 서비스 × 4개 검사로 실제 발생). 단일 항목은 항상 성공하고,
**판단을 뺀 순수 기계 추출이 가장 안정적이다.**

### 반증 결과를 받은 뒤

- 명령 로그가 붙어 있는가. 산문만 있으면 안 돌린 것이다
- skip 수가 보고됐는가. 0 이라고만 하면 의심한다
- 잔여 위험이 비어 있으면 되묻는다 — "전부 검증했다"는 거의 항상 거짓이다
- **FAIL 을 완화해서 옮기지 않는다.** 내 판단이 깨졌으면 그렇게 보고한다

## 게이트 — 규칙은 기계가 지킨다

문서 규칙 중 **기계가 검사하지 않는 것은 반드시 썩는다.** 이 세션에서 문서-코드 드리프트를
여러 번 잡았는데 자동으로 잡힌 것은 0건이었다.

`scripts/check-docs.js` 가 강제하는 것:

| 검사 | 왜 |
|---|---|
| 상대 링크 실존 | 죽은 링크는 문서를 못 믿게 만든다 |
| `CLAUDE.md` 줄 수 상한 | 읽히는 크기 유지 |
| `CLAUDE.md` **바이트 상한** | 줄 수만 세면 줄을 늘려 우회된다(실측) |
| `CLAUDE.md` 이력 마커 0 | 날짜·PR 번호는 git 이 갖는다 |

**게이트를 우회하는 방법을 찾으면 게이트를 고친다.** 우회한 채로 두지 않는다.
